GNSS SOLUTIONS AS A WORKFLOW REFERENCE; VRS INVESTIGATION

NEW IN 0.18.0 - EXPERIMENTAL FLOAT VRS
The existing GNSS dialog can now create an EXPERIMENTAL three-reference FLOAT
VRS from three reviewed physical BASE sources. It reuses the raw catalogue,
source inspection, background queue, static solver, map and result review.
The rover observations and known control are held out of the network fit.
Explicit ITRF2020 marker XYZ, individual coordinate epochs, matching GPS 1C/2W,
30 s expanded RINEX, navigation and receiver NOAZI ANTEX are required.

Our joint double-difference GLS estimates per-block FLOAT ambiguities with
shared master/pivot observation covariance. Relative dispersive and
nondispersive terms are transferred affinely to an explicitly defined ideal
virtual endpoint. This is not averaging baseline coordinates or independent
pairwise atmospheric states. Negative weights/extrapolation remain visible;
exactly three stations cannot check spatial curvature internally.

Virtual phases contain non-integer network biases. Downstream integer fixing
is forced OFF (v8); FLOAT results cannot pass the existing FIX baseline gate.
Physical ITRF2020 comparisons may also explicitly use AR OFF (v7). Existing
legacy profiles retain their contracts. No coordinates or independent baseline
are automatically accepted. Imported virtual points have no accepted national
coordinates; the defined global XYZ remains in the processing model.

The separate pinned kernel uses RTKLIB EX 2.5.1 geometry/broadcast ephemerides,
receiver PCO/NOAZI and hydrostatic mapping. Own wrapper/model code is GPLv3;
upstream BSD-2-Clause and SOFA terms/notices remain with the separate engine.
No engine binary, calibration or field data is distributed. Build locally with
tools/build_network_engine.py using the reviewed source/compiler, without
downloads or identity fallback. See docs/GNSS_SOLUTIONS_AND_VRS.txt.

Original physical references, navigation, calibration, source network, kernel
geometry, conditional joint covariance, exclusions and virtual observations
are retained in a local product. Static jobs snapshot it and reproduce geometry
and virtual RINEX on readback. Checksums are integrity, not authenticity.

This is a research prototype, not validated centimetre VRS. Reference clock
offsets are narrowly bounded; no general time correction/resampling, precise
SP3/CLK, full satellite patterns, tides, windup or integer network solution.
Conditional covariance excludes temporal, multipath, frame, base and transfer
model uncertainty. A successful run/FIX/formal sigma is not field accuracy.
Use withheld controls and physical-reference comparisons before any survey use.

USING THE EXPERIMENTAL GENERATOR
1. Import three physical BASE sources and a separate ROVER/NAV through existing
   GNSS import. Use the same reviewed occupation/session and source time system.
2. Open PPK/static -> Three-reference network / experimental FLOAT VRS.
   Enter each reference XYZ/ITRF2020 evidence and decimal coordinate epoch.
   The target is a defined approximate global virtual location, not a control fit.
   Saved reference reviews can prefill fields; explicit review remains required.
3. Check Generate EXPERIMENTAL FLOAT VRS; choose separately built network kernel,
   original reference receiver ANTEX and an existing NAV link. Document model,
   clock, uncertainty and calibration/licence review. Save to a NEW local folder.
4. Optional attachment uses the SAME typed raw import and creates one virtual
   reference point. Original physical sources and Check point stay intact.
   Static GPS L1/L2, upstream EX, ITRF2020, AR OFF and virtual zero pattern are
   selected. Review rover ARP/model and all four review boxes before processing.
5. Run static through the existing queue. Inspect epochs/map/report; compare a
   selected epoch with the existing held-out known point through the reviewed
   national-frame/HREF comparison. FLOAT cannot become an accepted baseline.

MODEL AND NEXT RESEARCH
GPS 1C/2W only; 30 s expanded continuous RINEX 3.04/3.05, three physical points,
4-16 common satellites/block and 30-120 samples. LLI/geometry-free screening can
exclude entire blocks. Every block resets virtual ambiguity arcs. No invented
Doppler/SNR. NAV, receiver model and original H/E/N are used once; a mathematical
zero-pattern virtual endpoint is not a manufactured receiver calibration.
Reference coordinate epochs must agree within 60 s. No velocity propagation.
The bounded initial clock model requires RCV CLOCK OFFS APPL 0, supplied reference
offsets <=10 ns and independent SPP clock magnitudes <=100 ns; DD cancellation
does not establish exact physical synchronisation or correct arbitrary clocks.
Conditional noise: code 0.35/0.45 m, phase 0.004/0.005 m divided by sin(elevation).
It is an assumed observation model, not measured field uncertainty. The pivot
defines a relative clock/atmosphere gauge. Affine extrapolation cannot recover
unobserved atmospheric curvature. Float ambiguities can absorb code/model bias.
The next numerical work is robust network arc/ambiguity treatment, improved
atmosphere/orbits and independent controls; do not enable integer fixing on this
product or suppress a worse withheld result to obtain an apparent improvement.

CURRENT STATIC / REFERENCE FOCUS - 0.16.0, 2026-10-21
The user primarily calculates stationary 30-100 km baselines and uses own bases,
Onocoy, Emlid Caster and https://igs.bkg.bund.de/. Dynamic tilt/3D development
has been stopped. Extend the same static processing/reference/quality workflow.
An experimental static GPS L1/L2 ionosphere/wet-delay profile is implemented;
see PPK_STATIC.txt for the constructed 60 km test and actual remaining limits.

Own base: use its original OBS/NAV with simultaneous occupation, documented
coordinates/frame/realisation/epoch, antenna/radome/serial and marker-to-ARP H/E/N.
Do not replace known controls with header approximate XYZ or average RTK output.

BKG: its data centre provides observation/navigation RINEX, station logs and
products including SP3, CLK, ERP and SINEX. Existing bounded RINEX import can read
supported expanded .rnx/.obs/.o and gzip data. BKG often supplies compact Hatanaka
.crx/.d (also gzip): expand with an appropriate reviewed converter first, keeping
originals and conversion evidence. The plugin does not currently expand Hatanaka,
download reference data or process precise SP3/CLK/SINEX/ERP products. A product
being available at BKG does not establish that this plugin processes it.

Emlid Caster relays NTRIP reference data. A connection/account is not a historical
RINEX archive or a locally generated network VRS. For postprocessing, preserve raw
base data at the receiver or a permitted complete RTCM recording, OBS/NAV conversion
and station/epoch/antenna identity. Emlid Studio documents raw-to-RINEX conversion;
this plugin does not yet record/convert live caster traffic.

Onocoy documentation describes single-base RTK and a roaming mountpoint with
handover/fallback. Preserve the actual station ID and frame choice for EACH
continuous segment; do not assume the caster name identifies one unchanged base.
Onocoy documents global frame options. Never label those EUREF89 merely because
the survey is in Norway. Review actual service output frame, realisation and
coordinate epoch; this plugin supplies no automatic ITRF/IGS/WGS84-to-EUREF shift.

VRS: distinguish supplied virtual-reference raw observations from synthesizing
a new VRS using a physical reference network. The single-base EX engine is not
relabeled as a VRS generator. Supplied VRS still needs documented coordinate,
frame/epoch, observation model, station continuity, antenna treatment and shared
network dependence. This release adds reference guidance, not a new VRS source
adapter, online service, multi-station model or independent VRS validation.

Real files and results stay local and out of GitHub/releases. Manufacturer-specific
branding must not restrict the general RINEX workflow to Emlid receivers.

AGREED REUSE-FIRST SCOPE
The user requires reuse and improvement of existing functions, with new code
only for useful missing capabilities. GNSS Solutions is a workflow reference.
Future raw-data support extends the existing GNSS/network workflow and common
import path. It must not create another parallel import, project store, map,
quality calculation, report, delivery workflow or GNSS Solutions tab.

Reuse map before implementation:
- Coordinate tables and column mapping: core.py and coordinate_job.py, with
  existing coordinate/repeatability consumers retaining their stated meaning.
- Processed relative POS/vector CSV: baselines.py and the existing import review,
  audit, fingerprint and duplicate-observation checks. Reopening a source for
  inspection must not add it to the inventory again. Renamed/re-exported source
  data and relabelled sessions must not create artificial independent repeats.
- Points, sessions, observation roles and saved inventory: network.py/network_ui.py.
- Verified SALSA adjustment, covariance, residuals and checks: existing network
  quality and mixed-survey components, with their current model limitations.
- QGIS map/selection and local reference-reviewed exports: network_map.py and
  delivery.py. Improve those components when a new input needs more metadata.

Implemented useful additions in 0.9.0 are bounded RINEX-specific decoding,
raw-file/station/antenna/time review and coverage/overlap views. A reviewed
RTKLIB EX GPS raw-processing adapter is implemented in 0.10.0. Route a supported processed result
through the existing baseline review/import contract with preserved source and
processing identity. Do not invent covariance or import every correlated epoch.
Raw carrier-phase observations, absolute coordinates and relative baselines
remain different data products; one shared import workflow does not erase this.
Document the existing owner and the missing capability for every proposed change.
VRS remains separately scoped research rather than part of the first addition.

WORKFLOW IDEAS
The manufacturer's GNSS Solutions Reference Manual describes coordinated
project/workbook, survey map and observation time views. Selecting data in
context and inspecting processing results is a useful design reference.

For an independent QGIS workflow, the practical progression is:
1. Existing 0.5.0 foundation: immutable network snapshots, explicit controls and
   observation roles, full-covariance GNSS adjustment, local quality reports,
   point uncertainty, residual/redundancy tables and held-out checks.
2. Implemented in 0.6.0 (original roadmap point 4): linked QGIS point/baseline layers and record
   selection; horizontal confidence ellipses, height uncertainty and residual
   graphics with explicit scales. Show raw, adjusted, excluded and check roles
   clearly; distinguish user warnings from statistical model tests. Links must
   open the original record and provenance. Compare saved alternative runs
   without silently updating the underlying measurements or control points.
   See NETWORK_MAP.txt for the actual profile, display scaling and limitations.
3. Implemented in 0.9.0: existing GNSS/network workspace now includes raw-file
   catalogue entries, station/antenna/time review, time coverage/overlap and
   satellite/observation availability. Jobs for a separately reviewed processing
   engine are implemented in 0.10.0 for pinned RTKLIB EX GPS. Inventory,
   processed-solution import and downstream checks are reused. Final coordinates
   and processed baseline vectors must remain different data products.

VRS IN GNSS SOLUTIONS
The manufacturer's manual, chapter 14, printed pages 231-237 (PDF pages
245-251), describes postprocessed VRS as synthesizing a virtual base raw-data
file for a chosen location or observation file from simultaneous surrounding
reference-station recordings. That product requires at least three stations.
Its distance guidance and station-selection defaults are product-specific,
not universal modern GNSS accuracy limits. The manual also explains that an
apparently short virtual baseline does not remove dependence on the physical
network's geometry and errors.

This is more than averaging station coordinates or exporting a nearby virtual
point. A usable synthetic carrier-phase observation stream requires a suitable
network observation/error model and independently validated output. The current
SALSA interface consumes processed observations; it supplies no VRS synthesis
in this plugin.

Separate two potential products:
- Offline virtual-reference observations: read simultaneous local RINEX files,
  synthesize an observation file at an explicitly chosen position, then process
  the rover against it. This is the most relevant research target for an
  office/QGIS workflow with locally held recordings.
- Real-time network corrections: continuous multi-station processing and a
  correction stream/NTRIP service. This also needs service operation, latency,
  protocol and access management. It is a separate engineering scope; an NTRIP
  client or a calculated virtual point alone is not such a service.

INPUTS TO REVIEW BEFORE AN OFFLINE VRS PROTOTYPE
- Time-overlapping raw reference observations from a surrounding network and
  the rover, with enough common satellites/signals and documented time systems.
  Design around three or more reference stations for the initial investigation;
  adequacy still depends on geometry, data and the chosen engine/model.
- Trusted physical station coordinates, reference frame/realisation and epoch,
  ellipsoidal heights, antenna identities, reference-point heights/offsets and
  applicable calibration models. Do not infer a coordinate epoch from file date.
- Required navigation/ephemeris and other products supported by the engine,
  with their provenance and permitted use. Remote products may be acquired
  only through an explicit separate workflow; measurements remain local.
- Virtual station location, requested time interval/interval spacing, desired
  output format and all model choices. Missing required information must stop
  a final calculation rather than silently receive default precision values.

ENGINE AND VALIDATION WORK STILL REQUIRED
Select an engine only after checking actual multi-station/VRS capabilities,
license, dependency redistribution, active maintenance and reproducible test
outputs. No engine has been selected or bundled for this purpose. A normal
single-base RTK/PPK solver must not be labelled a VRS engine without evidence.

Start with synthetic and permitted public benchmark observations. Compare
with a trusted independent implementation and held-out physical stations;
examine time gaps, cycle slips, ambiguity behaviour, geometry and atmosphere.
Propagate/model shared network dependence: rover baselines made from one VRS
are not automatically independent observations for least-squares adjustment.
Verify antenna/reference points, frame/epoch, timing, units, RINEX metadata and
round-trip readback. Record engine/model/input checksums and all exclusions.
Do not claim improved field accuracy from a successful file-generation test.
